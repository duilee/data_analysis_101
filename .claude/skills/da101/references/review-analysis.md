# 리뷰 분석 — 숫자가 말해주지 않는 Why 읽기

**챕터**: `10_숫자가_말해주지_않는_Why를_읽는_법/` · 노트북: `review_analysis.ipynb`

## 이 방법이 푸는 문제

지표는 "무엇이 떨어졌는지"는 알려주지만 "왜"는 알려주지 않는다. 커머스 상품 리뷰
(정성 데이터)에서 별점 5점(만족)과 1점(불만) 집단의 언어 차이를 여러 렌즈로 비교하고,
반드시 원문으로 돌아와 확인한다:

전처리·형태소 분석(kiwipiepy) → 빈도·워드클라우드(+유니크 키워드) → 변별 키워드
(TF-IDF·로그 오즈비 z-score) → 맥락·관계(바이그램, 동시출현 네트워크) → 토픽 모델링(LDA) →
원문 회귀(KWIC, 토픽별 대표 리뷰) → 긍정 리뷰의 재발견.

## 실행·검증

```bash
python generate_data.py      # data/reviews.csv 생성
jupyter nbconvert --to notebook --execute --inplace review_analysis.ipynb
```

- 입력: `data/reviews.csv` (`review_id, product_id, rating, text, created_at`).
- **기대 결과**: 생성기가 별점별 어휘 차이(불만: 배송·품질·환불 시나리오 / 만족 시나리오)를
  심어 두었으므로, 변별 키워드·LDA 토픽이 그 심어둔 주제 구분을 복원해야 한다.
- **주의 (버전 민감)**: `kiwipiepy==0.23.2`, `scikit-learn==1.9.0` 고정. 형태소 분리와
  TF-IDF·LDA 결과가 버전에 따라 달라지므로, **독자의 결과가 책과 다르면 가장 먼저 이 두
  패키지 버전을 확인**한다.
- 이 챕터는 데이터 파일이 있는 챕터 중 유일하게 DuckDB/SQL을 쓰지 않는다(pandas 직접 처리).
  책 본문의 임베딩 군집화(sentence-transformers)·LLM 코딩은 무거운 의존성/API 키 문제로
  노트북에서 의도적으로 생략되었다 — 독자가 물으면 이 사실을 알려준다.

## 내 데이터에 적용 — 인터랙티브 프로토콜

아래 1→5 순서로 진행한다. 각 단계 결과를 독자에게 보여주고 확인한 뒤 다음으로 간다.
노트북에 `[내 데이터 적용]` 주석이 11곳으로 가장 잘 표시된 챕터다 — 그 지점을 따라가되,
⚠ 집단 정의가 두 셀에 중복된 점만 추가로 주의한다.

### 1. 인테이크 — 독자에게 물을 것

- 텍스트 데이터의 **파일 경로**는? (앱 스토어 리뷰, CS 문의, NPS 서술형, 설문 주관식 모두 가능)

| 역할 (노트북 예시명) | 타입 | 의미 | 필수 |
| --- | --- | --- | --- |
| `text` | TEXT | 분석할 원문 | 필수 |
| `rating` | INT 등 | 집단을 가를 축 | 필수* |
| `created_at` | DATE | 작성 시점 (시계열 분석용) | 선택 |

  *별점이 아니어도 된다 — 잔존/이탈, 프로모터/디트랙터 등 어떤 이분 축이든.
- **비교할 두 집단의 정의**는? (이 정의가 분석의 뼈대다. 예: `rating == 5` vs `== 1`,
  중간 별점은 버릴 것인지도 함께)
- 도메인 **불용어**(서비스명, 상투어)와 **고유 명사**(제품명, 기능명 — 형태소 분석기 사용자
  사전에 등록할 것)는?
- 리뷰 건수는? — 집단당 **최소 수백 건** 권장 (미만이면 LDA·네트워크는 불안정, 빈도·변별
  키워드까지만 권한다).

### 2. 데이터 점검 — 통과 전 분석 시작 금지

```python
df = pd.read_csv("YOUR_CSV_PATH")
df.groupby("YOUR_RATING_COL").agg(n=("YOUR_TEXT_COL", "count"),
    avg_len=("YOUR_TEXT_COL", lambda s: s.str.len().mean()))
```

- 통과 기준: 두 집단 각각 수백 건 이상, 평균 길이 확인(한 단어짜리 리뷰 비중이 높으면 경고),
  중복 리뷰·봇 패턴(동일 문장 반복) 확인. 집단 간 건수가 극단적으로 불균형하면 변별 지표
  해석 시 주의를 안내한다.

### 3. 코드 치환 지도

| 앵커 (절/식별자) | 무엇을 | 어떻게 |
| --- | --- | --- |
| 로드 셀 | `data/reviews.csv` 경로, `rating`/`text`/`created_at` 컬럼명 | 독자 데이터로 |
| ⚠ 집단 정의 | `GROUP_A = reviews["rating"] == 5` / `GROUP_B == 1` (로드 셀 한 곳) | 독자 정의로 — TF-IDF 셀의 `is_pos`/`is_neg`는 `GROUP_A/B`를 재사용하므로 따라 바뀐다 |
| 전처리 셀 | `STOPWORDS`(7개 기본), `kiwi.add_user_word(...)` | 독자 도메인 불용어·고유명사로 확장 |
| 〃 | `tokenize()` 품사 규칙 (`NNG/NNP` 길이≥2, `VV/VA`→`~다`, 부정 `NEG_BEFORE/NEG_AFTER`) | 기본 유지 권장 — 형용사 뉘앙스가 중요하면 확장 |
| 변별 셀 | `TOP = 100`(유니크 키워드), `log_odds_z(..., alpha0=1000)` | 데이터 크기에 맞게 |
| 네트워크 셀 | `TOPN = 25`(바이그램), `cooccurrence_network(top_edges=40, min_word=22, min_pair=12)`, `NET_DROP` | 리뷰 수에 비례해 min 값 조정 (적으면 낮춘다) |
| LDA 셀 | `CountVectorizer(max_df=0.5, min_df=10)`, `n_components=5` | 토픽 수는 5~15 시도, "사람 말로 네이밍되는 수준"에서 멈춘다 |
| ⚠ 토픽 검사 셀 | `doc_topic[:, 4]`·`[:, 2]` 하드코딩 인덱스 | 독자 데이터의 토픽 번호로 — n_components 바꾸면 반드시 함께 |
| 원문 회귀 셀 | `kwic(neg, "환불")`의 키워드 | 앞 단계에서 나온 독자 키워드로 |
| 긍정 재발견 셀 | `flat_words`(상투어 제외 목록) | 독자 도메인의 뻔한 말들로 재작성 |
| 폰트 블록 | OS별 `FONT` 경로 | 독자 환경에 맞게 (한글 깨지면 여기부터) |

### 4. 단계별 진행

1. 로드·집단 정의 → 건수 확인 → 형태소 분석 실행 → **토큰 상위 30개를 보여주고 오분리·
   불용어 누락을 독자와 점검** (여기 품질이 전체의 상한 — 필요하면 사용자 사전 보강 후 반복).
2. 빈도·워드클라우드 → 유니크 키워드 → 첫 인상 합의.
3. 변별 키워드(TF-IDF, 로그 오즈비) → 상위 단어 표 제시, 빈도 결과와 무엇이 달라졌는지 설명.
4. 바이그램·동시출현 네트워크 → 커뮤니티(주제 덩어리) 읽기.
5. LDA → 토픽별 상위 단어로 네이밍 시도 → 안 되면 `n_components` 조정 후 반복.
6. **원문 회귀**: 핵심 키워드 KWIC + 토픽별 대표 리뷰를 반드시 읽고, 인용문을 근거로 결론 정리.
7. (여유가 있으면) 긍정 집단 재발견 — 몰랐던 쓰임새·고객군 탐색.

### 5. 결과 해석

- 어떤 렌즈의 결과든 **원문 확인을 거친 뒤에만** 보고에 쓴다. 키워드·토픽은 가설이고, 근거는
  원문 인용이다.
- 보고 형식 권장: "불만 집단은 {주제}를 {변별 키워드}로 말한다 — 대표 원문: '…'" 구조.
- 빈도를 전체 고객 비율로 읽지 않는다 (리뷰 작성자의 자기선택 편향).

## 함정

- 한국어 형태소 분석 품질이 전체 파이프라인의 상한이다 — 오분리가 보이면 사용자 사전부터.
- 리뷰는 극단 경험자가 더 쓴다 — 집단 간 비교(상대 비교)는 유효하지만 절대 비율 해석은 금물.
- LDA 토픽 수를 늘리면 그럴듯한 토픽이 계속 나온다 — 네이밍 불가능한 토픽이 나오면 멈춘다.

## 학습 가이드

### 핵심 개념 — 이 챕터를 마치면 설명할 수 있어야 하는 것

- **형태소 분석** — 한국어를 의미 단위(체언·용언)로 쪼개는 전처리. 띄어쓰기 토큰화로는
  조사·활용 때문에 같은 말이 다른 토큰이 된다.
- **변별 키워드 vs 빈도** — 많이 나오는 말(빈도)과 두 집단을 **가르는** 말(TF-IDF·로그 오즈비)
  은 다르다. "배송"이 양쪽에 다 많으면 변별력은 없다.
- **로그 오즈비 z-score** — 두 집단의 단어 사용 오즈 차이를 분산까지 고려해 표준화한 keyness
  지표. 저빈도 단어의 우연한 차이를 걸러 준다.
- **동시출현 네트워크** — 같은 리뷰에 함께 나오는 단어 쌍의 그래프. 단어 목록이 못 보여주는
  "무엇과 무엇이 묶여 불만인지"를 보여준다.
- **LDA 토픽 모델링** — 문서를 잠재 주제의 혼합으로 보는 모델. 토픽은 단어 분포일 뿐,
  의미 부여(네이밍)는 사람 몫.
- **원문 회귀(KWIC)** — 정량 렌즈로 찾은 후보를 원문 문맥으로 검증하는 마지막 단계. 정성
  분석의 결론은 항상 원문 인용이 근거다.

### 개념 체크

1. 단순 빈도 상위 단어와 로그 오즈비 z-score 상위 단어는 무엇이 다른가? 왜 변별에는
   후자를 쓰는가?
   - 힌트: 빈도는 양쪽 공통 단어가 지배 — 변별은 "한쪽에서만 유난히" 쓰이는 정도를 잰다.
2. "원문 회귀" 단계가 없으면 어떤 오류가 보고서에 들어가게 되는가?
   - 힌트: 키워드의 문맥 오독 — "환불"이 '환불해 달라'(불만)인지 '환불이 빨랐다'(만족)인지는
     원문만 안다.
3. 긍정 리뷰 분석(마지막 실습)이 불만 분석과 다른 종류의 액션으로 이어지는 이유는?
   - 힌트: 불만은 수리(fix) 액션, 긍정은 발견(새 쓰임새·고객군 → 마케팅 메시지, 포지셔닝)
     액션으로 이어진다.
