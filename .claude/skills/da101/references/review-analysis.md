## 이 방법이 푸는 문제

지표는 "무엇이 떨어졌는지"는 알려주지만 "왜"는 알려주지 않는다. 커머스 상품 리뷰
(정성 데이터)에서 별점 5점(만족)과 1점(불만) 집단의 언어 차이를 여러 렌즈로 비교하고,
반드시 원문으로 돌아와 확인한다:

10.7.2 전처리·형태소 분석(kiwipiepy) → 10.7.3 빈도·워드클라우드 → 10.7.4 가중치(유니크 키워드,
TF-IDF·로그 오즈비 z-score) → 10.7.5 맥락·관계(바이그램, 동시출현 네트워크) → 10.7.6 토픽
모델링(LDA, 토픽 시계열) → 10.7.7 원문 회귀(KWIC, 토픽별 대표 리뷰) → 10.7.8 긍정 리뷰의 재발견.

**책 이론부 포인터** (자세한 설명은 책에서 읽게 안내한다; 노트북 절 번호는 책의 실습 절을 따르므로 이론부 번호와
다르다 — 이론 10.1 ↔ 10.7.2~10.7.3, 10.2 ↔ 10.7.4, 10.3 ↔ 10.7.5, 10.4 ↔ 10.7.6(10.4.2는 10.7.6 끝 `[노트북 보충]` 설명만),
10.5 ↔ 10.7.7, 10.6 ↔ 10.7.8)

- **도입** — 정량 데이터는 'What & How many', 정성 데이터(리뷰·후기·한줄평·CS 문의·설문·앱스토어
  리뷰·인터뷰)는 'Why & How'에 답한다. 정성 데이터는 비정형·주관적이고 양이 많아(10만 건을 사람이
  못 읽음) 체계적 분석 방법이 필요하다는 문제의식.
- **10.1 텍스트 빈도 분석** — 형태소 분석기(kiwipiepy 등)로 쪼갠 뒤 집단별 빈도 집계(표 10.1)와
  워드클라우드(그림 10.1). 한계: '사이즈·디자인·재질'처럼 양쪽에 다 나오는 단어는 해석 불가.
- **10.2 텍스트 가중치 분석** — 10.2.1 유니크 키워드(양쪽 공통어 제거, 그림 10.2) → 10.2.2 TF-IDF(표 10.2,
  '한 리뷰 안에서 중요한 단어'를 잴 뿐 두 집단을 가르는 지표는 아님) → 10.2.3 로그 오즈비
  (오즈→오즈비→로그로 대칭화; 다이버징 막대 그림 10.3; 저빈도어 과대평가를 막으려 z-score 표준화).
- **10.3 단어 연관성·네트워크** — 10.3.1 바이그램(표 10.3·그림 10.4; '사이즈→작다'처럼 맥락 복원, 단
  연속한 두 단어만 잡음) → 10.3.2 동시출현 네트워크(그림 10.5; 같은 리뷰 안 단어 쌍, 단순 빈도로 그리면
  hairball이라 PMI로 연결 강도 측정). 읽는 법: 허브 = 개선 레버리지, 덩어리 = 카테고리.
  바이그램은 '순서(표현의 흐름)', 동시출현은 '묶음(주제 덩어리)' — 보완적으로 쓴다.
- **10.4 주제·의미 분석** — 10.4.1 LDA 토픽 모델링(그림 10.6 토픽별 상위어, 표 10.4 리뷰별 토픽 비중,
  그림 10.7 시간에 따른 토픽 비중 변화). 10.4.2 감성 분석(ABSA, 10.4.2.1)·임베딩(10.4.2.2)·LLM(10.4.2.3)은 소개만.
- **10.5 원문 맥락 확인** — 원문으로 돌아가는 이유 3가지(신호 진위 확인·맥락 포착·뉘앙스 복원).
  KWIC(표 10.5; 글자 그대로 매칭이라 '반품'은 따로 검색)과 토픽별 대표 리뷰(표 10.6).
- **10.6 긍정 리뷰가 알려주는 것** — 불만은 납작하고 만족은 입체적. 5점 동시출현 네트워크(그림 10.8)
  에서 기획에 없던 쓰임새(캠핑·차박)와 고객 세그먼트(반려인) 발견 → 카피 재작성·변형 제품·채널
  확장 액션.
- **10.8 실습(클로드 코드)** — 10.8.1 리포지터리 가져오기 → 10.8.2 run · 10.8.3 apply · 10.8.4 qna · 10.8.5 quiz.
  `/da101 run|apply|qna|quiz 리뷰 분석` 또는 자연어("리뷰 분석 실습 진행해보자").
- **10.9 정리하며** — 기법과 분석 순서는 예시일 뿐: 대상이 CS 문의·설문이면 전처리부터, 영어면 도구가,
  수십만 건 규모면 토픽 수·임계값이 달라진다. 임베딩·LLM이 빠르게 표준이 되고 있어 도구는 바뀌지만,
  핵심은 불만 해소를 넘어 만족의 맥락에서 숨은 강점·새 타깃을 찾는 '분석적 시선'. (정리 표는 없다.)

## 내 데이터에 적용 — 인터랙티브 프로토콜

아래 1→5 순서로 진행한다. 각 단계 결과를 독자에게 보여주고 확인한 뒤 다음으로 간다.
노트북에 `[내 데이터 적용]` 주석이 12곳으로 가장 잘 표시된 장이다 — 그 지점을 따라간다.
집단 정의는 로드 셀 한 곳뿐이고 이후 모든 렌즈가 그 결과(`pos`/`neg`)를 재사용한다.

### 1. 인테이크 — 독자에게 물을 것

- 텍스트 데이터의 **파일 경로**는? (앱 스토어 리뷰, CS 문의, NPS 서술형, 설문 주관식 모두 가능)

| 역할 (노트북 예시명) | 타입 | 의미 | 필수 |
| --- | --- | --- | --- |
| `text` | TEXT | 분석할 원문 | 필수 |
| `rating` | INT 등 | 집단을 가를 축 | 필수* |
| `created_at` | DATE | 작성 시점 (시계열 분석용) | 선택 |

  *별점이 아니어도 된다 — 잔존/이탈, 프로모터/디트랙터 등 어떤 이분 축이든.
- **비교할 두 집단의 정의**는? (이 정의가 분석의 뼈대다. 예: `rating == 5` vs `== 1`,
  중간 별점은 버릴 것인지도 함께)
- 도메인 **불용어**(서비스명, 상투어)와 **고유 명사**(제품명, 기능명 — 형태소 분석기 사용자
  사전에 등록할 것)는?
- 리뷰 건수는? — 집단당 **최소 수백 건** 권장 (미만이면 LDA·네트워크는 불안정, 빈도·변별
  키워드까지만 권한다).

### 2. 데이터 점검 — 통과 전 분석 시작 금지

```python
df = pd.read_csv("YOUR_CSV_PATH")
df.groupby("YOUR_RATING_COL").agg(n=("YOUR_TEXT_COL", "count"),
    avg_len=("YOUR_TEXT_COL", lambda s: s.str.len().mean()))
```

- 통과 기준: 두 집단 각각 수백 건 이상, 평균 길이 확인(한 단어짜리 리뷰 비중이 높으면 경고),
  중복 리뷰·봇 패턴(동일 문장 반복) 확인. 집단 간 건수가 극단적으로 불균형하면 변별 지표
  해석 시 주의를 안내한다.

### 3. 코드 치환 지도

| 앵커 (절/식별자) | 무엇을 | 어떻게 |
| --- | --- | --- |
| 로드 셀 | `data/reviews.csv` 경로, `rating`/`text`/`created_at` 컬럼명 | 독자 데이터로 |
| 집단 정의 | `GROUP_A = reviews["rating"] == 5` / `GROUP_B == 1` (로드 셀 한 곳) | 독자 정의로 — 빈도·TF-IDF·네트워크가 전부 `GROUP_A/B`와 `pos`/`neg`를 재사용하므로 여기 한 곳만 바꾼다 |
| 전처리 셀 | `STOPWORDS`(7개 기본), `kiwi.add_user_word(...)` | 독자 도메인 불용어·고유명사로 확장 |
| 〃 | `tokenize()` 품사 규칙 (`NNG/NNP` 길이≥2, `VV/VA`→`~다`, 부정 `NEG_BEFORE/NEG_AFTER`) | 기본 유지 권장 — 형용사 뉘앙스가 중요하면 확장 |
| 변별 셀 | `TOP = 100`(유니크 키워드), `log_odds_z(..., alpha0=1000)` | 데이터 크기에 맞게 |
| 네트워크 셀 | `TOPN = 25`(바이그램), `build_cooccurrence(top_edges=40, min_word=22, min_pair=12)` 기본값(`cooccurrence_network()`는 래퍼), `NET_DROP` | 리뷰 수에 비례해 min 값 조정 (적으면 낮춘다) |
| LDA 셀 | `CountVectorizer(max_df=0.5, min_df=10)`, `n_components=5` | 토픽 수는 5~15 시도, "사람 말로 네이밍되는 수준"에서 멈춘다 |
| ⚠ 토픽 검사 셀 | `doc_topic[:, 4]`·`[:, 2]` 하드코딩 인덱스 | 독자 데이터의 토픽 번호로 — n_components 바꾸면 반드시 함께 |
| 원문 회귀 셀 | `kwic(neg, "환불")`의 키워드 | 앞 단계에서 나온 독자 키워드로 |
| 토픽 시계열 셀 | `reviews["created_at"]`, `to_period("W")` 주차 집계 | 날짜 컬럼이 없으면 셀 생략, 있으면 컬럼명·집계 단위 조정 |
| 긍정 재발견 셀 | `flat_words`(상투어 제외 목록), `cooccurrence_network(pos, …, top_edges=48, min_word=20)` 호출 인자 | 독자 도메인의 뻔한 말들로 재작성, 인자는 리뷰 수에 맞게 |
| 폰트 블록 (2곳) | 준비 셀의 `plt.rcParams["font.family"]` 분기 + 워드클라우드 셀의 `FONT` 파일 경로 | 독자 환경에 맞게 (한글 깨지면 여기부터) |

### 4. 단계별 진행

1. (10.7.1~10.7.2) 로드·집단 정의 → 건수 확인 → 형태소 분석 실행 → **예시 리뷰 토큰 2건과 `freq_top` 표
   (집단별 상위 15개)로 오분리·불용어 누락을 독자와 점검** (더 보고 싶으면
   `freq_terms(freq, n=30)`으로 늘린다. 여기 품질이 전체의 상한 — 필요하면 사용자 사전 보강 후 반복).
2. (10.7.3~10.7.4.1) 빈도·워드클라우드 → 유니크 키워드 → 첫 인상 합의.
3. (10.7.4.2~10.7.4.3) 변별 키워드(TF-IDF, 로그 오즈비) → 상위 단어 표 제시, 빈도 결과와 무엇이 달라졌는지 설명.
4. (10.7.5) 바이그램·동시출현 네트워크 → 커뮤니티(주제 덩어리) 읽기 — 허브 단어는 개선 레버리지 후보.
5. (10.7.6) LDA(+토픽 시계열) → 토픽별 상위 단어로 네이밍 시도 → 안 되면 `n_components` 조정 후 반복.
6. (10.7.7) **원문 회귀**: 핵심 키워드 KWIC + 토픽별 대표 리뷰를 반드시 읽고, 인용문을 근거로 결론 정리.
7. (10.7.8, 여유가 있으면) 긍정 집단 재발견 — 몰랐던 쓰임새·고객군 탐색.

### 5. 결과 해석

- 어떤 렌즈의 결과든 **원문 확인을 거친 뒤에만** 보고에 쓴다. 키워드·토픽은 가설이고, 근거는
  원문 인용이다.
- 보고 형식 권장: "불만 집단은 {주제}를 {변별 키워드}로 말한다 — 대표 원문: '…'" 구조.
- 빈도를 전체 고객 비율로 읽지 않는다 (리뷰 작성자의 자기선택 편향).
- 불만에서 나온 운영 이슈는 고쳐야 본전(별점 복구)이고, 만족에서 발견한 의외의 쓰임새·고객군은
  성장 동력(카피·변형 제품·채널)으로 번역한다.
- 네트워크의 허브 단어(예: '환불')는 개선 레버리지 — 하나를 손보면 매달린 불만이 함께 풀린다는 가설.
  덩어리는 데이터가 스스로 찾은 분류라 토픽 모델링·CS 티켓 자동 분류의 카테고리 후보로 쓴다(책 10.3.2).
- 다음 액션: 불만 주제를 CS·제품 개선 백로그로 잇고, 개선 효과는 A/B 테스트(3장)로 검증한다
  (책 10.9는 기법·순서가 예시일 뿐이라는 점과 '분석적 시선'을 강조한다 — 백로그·A/B 연결은 이 레퍼런스의 제안).

## 함정

- 한국어 형태소 분석 품질이 전체 파이프라인의 상한이다 — 오분리가 보이면 사용자 사전부터.
  전처리·정제가 정성 분석에서 가장 시간이 걸리는 단계다.
- 리뷰는 극단 경험자가 더 쓴다 — 집단 간 비교(상대 비교)는 유효하지만 절대 비율 해석은 금물.
- TF-IDF 상위어를 "집단을 가르는 단어"로 읽지 않는다 — 양쪽 공통어가 여전히 상위에 남는다.
  가르는 정도는 로그 오즈비 z-score로 잰다(표준화 없이는 한두 번 나온 단어가 극단값이 된다).
- 바이그램은 연속한 두 단어만 잡는다("배송이 예상보다 느려요"의 배송–느리다는 놓침). 동시출현을
  단순 빈도로 이으면 hairball — PMI로 걸러야 덩어리가 보인다.
- LDA 토픽 수를 늘리면 그럴듯한 토픽이 계속 나온다 — 네이밍 불가능한 토픽이 나오면 멈춘다.
  토픽 번호·구성은 실행 환경(버전·seed)에 따라 달라진다.
- 추상화 수준이 높아질수록 원문 맥락이 사라진다 — 반어("환불도 안 해 주길래 그냥 쓰는데
  괜찮네요")는 원문을 봐야 걸러진다. KWIC은 글자 그대로 매칭이라 유의어('반품')는 따로 검색.
- 단어 기반 렌즈(빈도·가중치·네트워크·LDA)는 글자가 같아야 같은 것으로 본다 — '배송/배달',
  '환불/반품'은 따로 세어지고, "아주 빠른 배송이네요, 2주나 걸렸지만" 같은 반어는 못 잡는다(책 10.4).
  의미 단위로 묶으려면 임베딩·LLM(노트북 미포함).
- 분석 대상(CS 문의·설문·영어 데이터)이 바뀌면 전처리·도구도 다시 잡고, 수십만 건 규모로 커지면
  토픽 수·임계값(min_df, min_word·min_pair)을 재조정한다(책 10.9).

## 학습 가이드

### 핵심 개념 — 이 장을 마치면 설명할 수 있어야 하는 것

- **형태소 분석** — 한국어를 의미 단위(체언·용언)로 쪼개는 전처리. 띄어쓰기 토큰화로는
  조사·활용 때문에 같은 말이 다른 토큰이 된다.
- **변별 키워드 vs 빈도** — 많이 나오는 말(빈도)과 두 집단을 **가르는** 말(TF-IDF·로그 오즈비)
  은 다르다. "배송"이 양쪽에 다 많으면 변별력은 없다.
- **로그 오즈비 z-score** — 두 집단의 단어 사용 오즈 차이를 분산까지 고려해 표준화한 keyness
  지표. 저빈도 단어의 우연한 차이를 걸러 준다.
- **동시출현 네트워크** — 같은 리뷰에 함께 나오는 단어 쌍의 그래프. 단어 목록이 못 보여주는
  "무엇과 무엇이 묶여 불만인지"를 보여준다.
- **LDA 토픽 모델링** — 문서를 잠재 주제의 혼합으로 보는 모델. 토픽은 단어 분포일 뿐,
  의미 부여(네이밍)는 사람 몫.
- **원문 회귀(KWIC)** — 정량 렌즈로 찾은 후보를 원문 문맥으로 검증하는 마지막 단계. 정성
  분석의 결론은 항상 원문 인용이 근거다.

### 개념 체크

1. 단순 빈도 상위 단어와 로그 오즈비 z-score 상위 단어는 무엇이 다를까요? 두 집단을 비교할 때
   왜 후자를 쓸까요?
   - 힌트: 빈도는 양쪽 공통 단어가 지배 — 변별은 "한쪽에서만 유난히" 쓰이는 정도를 재고,
     z-score 표준화가 저빈도어의 우연한 쏠림을 걸러 준다.
2. 키워드·토픽 분석이 끝났는데 "원문 회귀" 단계를 건너뛰고 보고서를 쓰면, 어떤 종류의 오류가
   들어갈 수 있을까요? '환불'이라는 변별 키워드를 놓고 생각해 보세요.
   - 힌트: 키워드의 문맥 오독 — "환불"이 '환불해 달라'(불만)인지 '환불이 빨랐다'(만족)인지,
     반어인지는 원문만 안다. 숫자가 뭉뚱그린 뉘앙스("하루 늦음" vs "2주째")도 원문에서만 산다.
3. 띄어쓰기로 토큰을 나누지 않고 형태소 분석기를 쓰는 이유는 무엇일까요? 노트북이 '연락이 안
   되다'를 '되다(부정)'으로 따로 표시하는 이유도 함께 설명해 보세요.
   - 힌트: 교착어 — '배송이/배송도/배송은'이 같은 '배송'으로 모여야 센다. 부정어를 살리지 않으면
     '되다'와 '안 되다'가 같은 토큰으로 뭉개져 불만 신호가 사라진다.
4. 바이그램 네트워크와 동시출현 네트워크는 그림이 비슷한데, 답하는 질문이 어떻게 다를까요?
   동시출현 연결을 단순 빈도가 아니라 PMI로 잡는 이유는요?
   - 힌트: 바이그램 = 순서(표현의 흐름 "환불→요청→연락"), 동시출현 = 순서 무관한 묶음(주제
     덩어리). 단순 빈도는 '배송' 같은 흔한 단어가 모든 것과 이어져 hairball — PMI는 우연히 함께
     나올 정도 대비 실제 결합 강도를 잰다.
5. LDA 토픽 모델링은 동시출현 네트워크와 무엇이 같고 무엇이 다를까요? 토픽별 상위 단어를 얻은
   뒤 사람이 반드시 해야 하는 일은?
   - 힌트: 둘 다 함께 나오는 단어를 묶지만, LDA는 리뷰별 토픽 비중을 숫자로 주어 시간 추이 등
     집계가 가능하다. 토픽은 단어 분포일 뿐 — 이름 붙이기(네이밍)는 사람 몫이고, 번호·순서는
     환경에 따라 바뀐다.
