# 로그 모니터링 — 배포 뒤에 깨진 로그 찾기

**챕터**: `chapters/12_로그는_쌓고_있는데,_왜_전환율은_못_구해요/` · 노트북: `log_monitoring.ipynb`

## 이 방법이 푸는 문제

이벤트 택소노미(무엇을·어떤 이름으로·어떤 맥락과 함께 기록할지의 계약)가 맞아도 앱의 새 버전이 나가면 로그는
셋 중 하나로 조용히 깨진다 — 이벤트가 안 오거나(누락), 두 번 오거나(중복 발화), 오긴 오는데 값이 비어 있거나
(프로퍼티 누락). 문서에는 흔적이 없고 숫자만 바뀌므로, 문서 대조와는 별개로 **숫자를 지켜보는** 모니터링이 필요하다.

- 실습 1 일별 마트: 원본 로그 → 이벤트 마트(날짜·플랫폼·이벤트별 건수·유저 수) + 프로퍼티 채움률 마트((이벤트, 프로퍼티)별 not-null 비율). 모니터링은 raw가 아니라 이 마트 위에서 돈다.
- 실습 2 이벤트 수 이상: 기준일 D-2 vs 일주일 전 D-9(요일 효과 제거), |변화율| > 60% 그리고 한쪽 건수 > 최소 50건. 잡힌 이벤트의 30일 추세 그림.
- 실습 3 프로퍼티 채움률 이상: 같은 두 날짜, not-null 비율 60% 넘게 하락(올라가는 쪽은 사고가 아니고, 기준일에 안 온 이벤트는 2단계 몫).
- 실습 4 리포트: 📉 감소 / 📈 증가 / 🕳️ 채움률 하락 세 묶음을 슬랙 mrkdwn 텍스트로. 전송은 `requests.post(WEBHOOK_URL, …)` 주석 한 줄.

## 실행·검증

```bash
python generate_data.py      # data/*.csv 3개 (SEED=11, 유저 3,000명 × 30일, event_log ≈ 17만 행)
jupyter nbconvert --to notebook --execute --inplace log_monitoring.ipynb
```

- 입력: `data/event_log.csv`(event_time, user_id, platform, app_version, event_name, screen_name, properties JSON),
  `data/taxonomy_events.csv`, `data/taxonomy_properties.csv`(scope·data_type·allowed_values·events).
- SQL 파일(인라인과 동일): `sql/mart_event_daily.sql`, `sql/mart_event_param_daily.sql`, `sql/event_count_anomaly.sql`, `sql/param_null_anomaly.sql`.
- **기대 결과** (생성기가 8/25 3.5.0 배포에 심은 사고 5종 — 표준 문턱 ±60%·최소 50건으로 모두 잡힘):
  - 실습 2 📉: Android·iOS `subscription_renewed` 83/76 → 0 (−100%, 서버 갱신 배치 중단 — 양 플랫폼 동시), iOS `tap_content_card` 330 → 103 (−68.8%), Android `page_view_home` 297 → 105 (−64.6%)
  - 실습 2 📈: Android `view_content_card` 1,048 → 2,312 (+120.6%, 중복 발화)
  - 실습 3: iOS `page_view_content_detail`의 `content_id` 채움률 100% → 28.6% (−71.4%) — 이벤트 수는 330 → 350으로 늘었는데 값만 빔. 기준일에 오지 않은 이벤트(구독 갱신)는 3단계 대상에서 제외(2단계 몫)
  - 실습 4 리포트 아홉 줄(감소 4·증가 1·채움률 1). 마트 크기: 원본 172,458행 → 이벤트 마트 1,426행 · 프로퍼티 마트 1,486행
- 부록 `extra/taxonomy_check.py`(extra/ 안에서 실행): 문서 규칙 검사(접두어·snake_case·설명·enum 허용값·유저 프로퍼티 후보) + 문서 vs 로그 대조(미등록·죽은 이벤트·enum 이탈·플랫폼 비대칭). 이 데이터에는 심어 둔 결함이 없어 요청서 0건이 정상.

## 내 데이터에 적용 — 인터랙티브 프로토콜

### 1. 인테이크
- 일별 이벤트 마트가 이미 있는가(테이블 이름·열: 날짜·플랫폼·이벤트명·건수), 없으면 원본 로그의 열(프로퍼티가 JSON 한 칸인지 열로 펼쳐졌는지).
- 지난 배포일. 기준일은 배포 뒤 최소 D-2(늦게 도착하는 이벤트), 비교일은 그 일주일 전.
- 하루 이벤트 규모 → 최소 건수. 놓치면 안 되는 핵심 이벤트(홈 진입·결제·구독 갱신) 목록 → 별도 낮은 문턱.
- 결과 형식: 표 / 슬랙 텍스트 / 웹훅 전송(환경변수로 받음. 웹훅 URL을 코드·노트북에 적지 않는다).
### 2. 매핑 확인
`params`(기준일·비교일·문턱·최소 건수·핵심 목록)와 열 매핑 표를 먼저 보여주고 확인받는다.
### 3. 실행
실습 1(마트가 없을 때만) → 2 → 3 → 4. 프로퍼티 마트의 키 목록은 독자의 택소노미 문서에서, 없으면 로그 JSON 키 빈도 상위에서 만든다.
### 4. 결과 검증
잡힌 항목마다 30일 추세를 그려 배포일에 꺾이는지 확인. 캠페인·요일 효과로 설명되는 변동은 "정상 변동"으로 표시.
### 5. 결과 해석
회귀(핫픽스 요청) / 의도된 변경인데 문서가 안 따라옴(요청서) / 정상 변동 셋 중 하나로 분류해 돌려준다.

## 함정

- 어제(D-1)를 기준일로 잡으면 아직 도착하지 않은 로그 때문에 모든 이벤트가 빠져 보여 가짜 알림이 난다. received_time − event_time 분포로 우리 서비스의 지연을 먼저 본다.
- 어제와 비교하면 요일 효과가 섞인다. 같은 요일(일주일 전)과 비교한다.
- 최소 건수는 하루 열 건 안팎짜리 이벤트의 우연한 두 배·반 토막을 거른다(예: `tap_theme_toggle` 4~16건). 규모가 작은데 중요한 이벤트가 있으면 전체 문턱을 낮추지 말고 그 이벤트만 별도 목록으로 두고 문턱을 따로 정한다.
- `LEFT JOIN`은 일주일 전(d8) 기준이어야 기준일에 0건인 이벤트(−100%)가 결과에 남는다. 새로 생긴 이벤트는 이 쿼리로 안 잡힌다(부록의 미등록 이벤트 검사 몫).
- 이벤트 수만 보면 실습 3의 사고(수는 늘고 값만 빔)를 못 잡는다. 채움률은 항상 같이 본다.
- 1×1 코드 표에 실행 결과를 넣지 않는다(책 규칙). 웹훅·사내 테이블명을 노트북에 남기지 않는다.

## 학습 가이드

### 핵심 개념
이벤트 유형 넷과 접두어(page_view_/tap_/view_/system_) · 이벤트 프로퍼티 vs 유저 프로퍼티("이벤트가 안 일어나도 존재하는 값인가") · 컨텍스트와 screen_name 계층 · 문서 vs 로그의 벌어짐 4종 · 배포 회귀 3종과 모니터링 지표 3종 · 임계값(±60%·최소 건수·D-2·같은 요일)의 트레이드오프.
### 개념 체크
1. 홈 배너에 tap_main_banner만 있고 view_main_banner가 없을 때 계산할 수 없는 지표는? 2. 이벤트 수는 늘었는데 분석이 막히는 배포 사고는 무엇이고 어느 지표로 잡나? 3. 왜 어제가 아니라 그저께를 기준일로 잡나? 4. 홈 진입은 Android만 빠지고 구독 갱신은 양쪽이 같이 0건이다 — 각각 어디서 난 사고인가?
### 심화 과제
`params`에 핵심 이벤트 목록과 낮은 문턱(예: ±25%, 최소 건수 예외)을 추가해 실습 2를 다시 돌리고, 열거형 프로퍼티(plan·content_type)의 값별 비율 변화를 같은 방식으로 감지하는 실습 5를 만들어 본다.
