## 이 방법이 푸는 문제

이벤트 택소노미(무엇을·어떤 이름으로·어떤 맥락과 함께 기록할지의 약속)가 맞아도 앱의 새 버전이 나가면 로그는
셋 중 하나로 조용히 깨진다 — 이벤트가 안 오거나(누락), 두 번 오거나(중복 발화), 오긴 오는데 값이 비어 있거나
(프로퍼티 값 유실). 문서에는 흔적이 없고 숫자만 바뀌므로, 문서 대조와는 별개로 **숫자를 지켜보는** 모니터링이 필요하다.

- 실습 1 일별 마트: 원본 로그 → 이벤트 마트(날짜·플랫폼·이벤트별 건수·유저 수) + 프로퍼티 채움률 마트((이벤트, 프로퍼티)별 not-null 비율). 모니터링은 raw가 아니라 이 마트 위에서 돈다.
- 실습 2 이벤트 수 이상: 기준일 D-2 vs 일주일 전 D-9(요일 효과 제거), |변화율| > 60% 그리고 한쪽 건수 > 최소 50건. 잡힌 이벤트의 30일 추세 그림(배포 전 평균 = 100 지수).
- 실습 3 프로퍼티 채움률 이상(책 제목은 "프로퍼티 누락 이상 감지"): 같은 두 날짜, not-null 비율 60% 넘게 하락(올라가는 쪽은 사고가 아니고, 기준일에 안 온 이벤트는 2단계 몫).
- 실습 4 리포트: 📉 감소 / 📈 증가 / 🕳️ 채움률 하락 세 묶음을 슬랙 mrkdwn 텍스트로. 이상이 없으면 "✅ 이상 없음" 한 줄을 보내 '이슈 없음'과 '실행 안 됨'을 구분한다. 전송은 `requests.post(WEBHOOK_URL, …)` 주석 한 줄.

**책 이론부 포인터** (QnA 모드는 요지만 말하고 자세한 설명은 책의 해당 절로 안내한다):
- 1절 도입 (표 1) — 'home'을 검색하면 page_view_home / home_view / HomeScreen 셋이 나오는 상황. 택소노미 = 제품과 데이터 사이의 약속. 방치 비용은 "찾지 못해 결정을 못 내리는 제품팀 + 히스토리 추적에 시간을 쓰는 분석가".
- 2절 택소노미의 구성 — 네 부분: 이벤트 / 이벤트 프로퍼티 / 유저 프로퍼티 / 컨텍스트. 2.1 로그 한 건 예시(JSON). 2.2 이벤트 유형 넷(화면 진입·탭/클릭·노출·시스템/서버)과 노출 이벤트를 남기기 전 질문 4개(분모로 쓰는 지표가 있나·바꿀 결정이 있나·page_view로 대신 못 하나·양을 감당하나). 2.3 클라이언트 vs 서버 이벤트 — 차이는 신뢰도, 결제·상태는 서버, 행동·맥락은 클라이언트; 클라이언트 유실은 감안하되 급변은 모니터링으로 잡는다. 2.4 (표 2) 이벤트 프로퍼티(그 순간의 맥락, 분해 축) vs 유저 프로퍼티(그 시점의 상태, 세그먼트 축). 2.5 컨텍스트(SDK 자동 수집)와 화면 계층 — 모든 이벤트 필수 프로퍼티로 screen_name(그림 1).
- 3절 택소노미 설계하기 — 3.1 전제 셋: 이벤트는 코드에 심기는 순간 제품의 일부(로깅·QA는 개발 프로세스의 한 단계) / 여러 직군이 쓰니 이름이 예측 가능해야 함 / 현재 상태 확인용이라 과거와 억지로 잇지 않음(로그 유통기한은 짧다, 서버 이벤트는 예외). 3.2 (표 3) 설계 순서 = 질문 → 지표 → 퍼널 → 이벤트/프로퍼티(온보딩 개편 예시, 바텀업으로 화면 요소마다 심는 게 흔한 실수). 3.3 (표 4) 이벤트 vs 프로퍼티 트레이드오프와 판별 질문 4개(한 선에 그릴 일이 있나·퍼널 단계인가 성격인가·구분값 집합이 열려 있나·필수 프로퍼티가 같나). 원칙: 이벤트는 의도가 담긴 행동 단위, 어디서·무엇에·어떤 조건은 프로퍼티.
- 4절 이름 붙이기 — 4.1 (표 5) 접두어 page_view_/tap_/view_/system_. 4.2 (표 6) 접두어_대상[_세부], snake_case 소문자, 이름에 화면·버전·플랫폼·약어 금지, 트리거 조건을 두세 문장으로 기록. 4.3 (표 7) 이벤트 프로퍼티 정의서 = 타입·필수 여부·값의 범위·예시; 프로퍼티 이름은 전역에서 한 뜻(content_id vs item_id, 'type' 재사용 금지); id·전화번호는 문자형; 불리언 표기 통일; 자주 같이 쓰는 프로퍼티는 번들. 4.4 유저 프로퍼티 = up_ 접두어, 갱신 정책(덮어쓰기·누적·최초값 유지), enum 허용값과 초기값, 카테고리 넷(settings·num_of_record·account·experiment).
- 5절 템플릿 (표 8~11) — 화면 / 이벤트 / 이벤트 프로퍼티 / 유저 프로퍼티 템플릿. 필요한 열(status·platform·note)은 추가해 쓴다.
- 6절 검증과 모니터링 — 6.1 (표 12) 문서와 로그의 벌어짐 4종: 미등록 이벤트 / 미배포·누락 이벤트 / 프로퍼티 누락·허용값 이탈 / 플랫폼 비대칭 — 문서와 로그를 나란히 놓고 차집합·허용값 대조·플랫폼 분포로 기계적으로 찾는다(일 1회 배치). 부록 `extra/taxonomy_check.py`가 이 절. 6.2 (표 13) 택소노미가 맞아도 깨지는 세 방식: 이벤트 수 급감(누락·SDK 초기화 실패·한쪽 플랫폼 배포 누락) / 급증(중복 발화·재시도 루프·자동 추적 중복) / 프로퍼티 값 유실(값 누락·키 이름 변경·타입 변경). 실습 2가 표 13의 첫 두 줄, 실습 3이 셋째 줄.
- 실습 절 — 최소 건수 50은 사내 기준(1만 건)을 실습 규모에 맞게 줄인 값이니 우리 서비스에서 다시 정한다. 기준일·비교일은 실습에서만 고정, 운영에서는 오늘 기준으로 계산.
- 정리하며 — 기억할 둘: 관리하지 않는 택소노미는 몇 달 안에 버려진다(로깅·QA를 개발 프로세스 안으로) / 처음부터 완벽한 택소노미는 없다(지금 질문에 답하게 만들고 새 질문이 생기면 추가, 과거와 억지로 잇지 않기). 정리 표: 질문 "로그가 있는데 왜 분석이 안 되는가" → 해결 "접두어로 유형 구분, 이벤트·유저 프로퍼티·컨텍스트 분리, 배포 뒤 모니터링" → 주의 "질문에서부터 설계, 꾸준한 문서 관리" → 다음 액션 "우리 일별 이벤트 마트로 지난 배포 전후 비교 → 이슈 해결로 데이터 거버넌스 확립".

## 내 데이터에 적용 — 인터랙티브 프로토콜

### 1. 인테이크 (책 Claude Code 실습 절의 질문 4개와 같은 순서)
- 마트 — 일별 이벤트 마트가 이미 있는가(테이블 이름·열: 날짜·플랫폼·이벤트명·건수), 없으면 원본 로그의 열(프로퍼티가 JSON 한 칸인지 열로 펼쳐졌는지).
- 날짜 — 지난 배포일. 기준일은 배포 뒤 최소 D-2(늦게 도착하는 이벤트), 비교일은 그 일주일 전.
- 문턱 — 하루 이벤트 규모 → 최소 건수(실습의 50은 축소값). 놓치면 안 되는 핵심 이벤트(홈 진입·결제·구독 갱신) 목록 → 별도 낮은 문턱.
- 결과 형식 — 표 / 슬랙 텍스트 / 웹훅 전송(환경변수로 받음. 웹훅 URL을 코드·노트북에 적지 않는다).
### 2. 매핑 확인
`params`(기준일·비교일·문턱·최소 건수·핵심 목록)와 열 매핑 표를 먼저 보여주고 확인받는다.
### 3. 실행
실습 1(마트가 없을 때만) → 2 → 3 → 4. 프로퍼티 마트의 키 목록은 독자의 택소노미 문서에서, 없으면 로그 JSON 키 빈도 상위에서 만든다.
### 4. 결과 검증
잡힌 항목마다 30일 추세를 그려 배포일에 꺾이는지 확인. 캠페인·요일 효과로 설명되는 변동은 "정상 변동"으로 표시.
### 5. 결과 해석
회귀(핫픽스 요청) / 의도된 변경인데 문서가 안 따라옴(변경 요청서) / 정상 변동 셋 중 하나로 분류해 돌려준다. 플랫폼 열로 앱 사고(한쪽 플랫폼)와 서버 사고(양쪽 동시)를 가른다.
책 정리하며의 다음 액션: 배포 전후 비교에서 잡힌 이슈를 해결하는 것이 데이터 거버넌스의 출발점 — 문서 vs 로그 대조(6.1, 부록)는 일 1회 배치로, 숫자 모니터링(6.2, 실습)은 주 2회 스케줄로 올리라고 안내.

## 함정

- 어제(D-1)를 기준일로 잡으면 아직 도착하지 않은 로그 때문에 모든 이벤트가 빠져 보여 가짜 알림이 난다. received_time − event_time 분포로 우리 서비스의 지연을 먼저 본다(대개 D-2면 95% 이상 도착). 지연 데이터를 마트에서 다루는 법은 11장 몫.
- 어제와 비교하면 요일 효과가 섞인다. 같은 요일(일주일 전)과 비교한다.
- 최소 건수는 하루 열 건 안팎짜리 이벤트의 우연한 두 배·반 토막을 거른다(예: `tap_theme_toggle` 4~16건). 규모가 작은데 중요한 이벤트가 있으면 전체 문턱을 낮추지 말고 그 이벤트만 별도 목록으로 두고 문턱을 따로 정한다.
- `LEFT JOIN`은 일주일 전(d8) 기준이어야 기준일에 0건인 이벤트(−100%)가 결과에 남는다. 새로 생긴 이벤트는 이 쿼리로 안 잡힌다(부록의 미등록 이벤트 검사 몫). 양방향이 필요하면 FULL OUTER JOIN.
- 이벤트 수만 보면 실습 3의 사고(수는 늘고 값만 빔)를 못 잡는다. 채움률은 항상 같이 본다.
- 문서 대조(6.1, 4종)와 숫자 모니터링(6.2, 3종)은 다른 검사다 — 문서와 로그가 일치해도 배포 뒤 숫자는 깨진다. 둘 다 돌린다.
- 클라이언트 이벤트의 일정 범위 유실은 감안할 것이지 막을 것이 아니다(책 2.3). 유실을 감안하기 어려운 결제·상태는 서버 이벤트로.
- 설계 단계 함정(책 3~4절): 화면 요소마다 바텀업으로 심기 / 노출 이벤트 남발 / 같은 뜻 다른 이름(content_id vs item_id) / id를 숫자 타입으로 / 불리언 표기 혼용 / 이름에 버전·플랫폼 넣기.
- 1×1 코드 표에 실행 결과를 넣지 않는다(책 규칙). 웹훅·사내 테이블명을 노트북에 남기지 않는다.

## 학습 가이드

### 핵심 개념
이벤트 유형 넷과 접두어(page_view_/tap_/view_/system_) · 클라이언트 vs 서버 이벤트(신뢰도) · 이벤트 프로퍼티 vs 유저 프로퍼티("이벤트가 안 일어나도 존재하는 값인가", up_ 접두어·갱신 정책) · 컨텍스트와 screen_name 계층 · 설계 순서 질문 → 지표 → 퍼널 → 이벤트/프로퍼티 · 이벤트 vs 프로퍼티 판별 질문 4개 · 이름 규칙과 프로퍼티 정의서(타입·필수·범위·예시) · 문서 vs 로그의 벌어짐 4종 · 배포 뒤 깨지는 3방식과 모니터링 지표 3종 · 임계값(±60%·최소 건수·D-2·같은 요일)의 트레이드오프.
### 개념 체크 (책 Claude Code 실습의 퀴즈 출제 범위 5개: 유형·접두어 / 이벤트·유저 프로퍼티 / 질문에서 거꾸로 설계 / 이름·정의서 / 지표 3종과 문턱)
1. 홈 배너에 tap_main_banner만 있고 view_main_banner가 없을 때 계산할 수 없는 지표는? 2. 이벤트 수는 늘었는데 분석이 막히는 배포 사고는 무엇이고 어느 지표로 잡나? 3. 왜 어제가 아니라 그저께를 기준일로 잡나? 4. 홈 진입은 Android만 빠지고 구독 갱신은 양쪽이 같이 0건이다 — 각각 어디서 난 사고인가? 5. 온보딩 3단계 화면 진입을 이벤트 셋으로 나눌지, 이벤트 하나 + step 프로퍼티로 둘지 — 어느 쪽이고 근거는(책 3.3 질문 4개)? 6. 가입일과 구독 플랜 중 유저 프로퍼티는 무엇이고 왜인가?
### 심화 과제
`params`에 핵심 이벤트 목록과 낮은 문턱(예: ±25%, 최소 건수 예외)을 추가해 실습 2를 다시 돌리고(책 예시: threshold 0.4로 낮추면 무엇이 더 걸리나), 열거형 프로퍼티(plan·content_type)의 값별 비율 변화를 같은 방식으로 감지하는 실습 5를 만들어 본다.
