## 이 방법이 푸는 문제

느린 쿼리, DW에 없는 데이터, 팀마다 다른 숫자는 쿼리 실력이 아니라 **데이터가 놓인 자리**의
문제다. 이 장은 가상의 구독형 앱 데이터(소스 다섯 개)로 네 층을 직접 쌓아 같은 질문
("일별 활성 구독자 수와 매출")을 raw와 마트에서 답해 보며 차이를 체감하게 한다.

- 11.6.2 raw: CSV 네 개(events 제외)를 한 쿼리(47줄)로 조인 — 정의가 쿼리 안에 흩어져 있어 사람마다 숫자가 달라지는 구조
- 11.6.3 staging: 소스 1:1 뷰 — 이름·타입·중복·시스템 이벤트만 정리, 비즈니스 로직 금지
- 11.6.4 dim/fact: 유저 일별 스냅샷·SKU 디멘션 + 거래 팩트(구독 이벤트) + 스냅샷 팩트(일별 활성 구독)
- 11.6.5 mart: 파티션(날짜) 하나씩 채우는 `run_partition()` 배치로 90일 backfill, 같은 질문을 3줄로
- 11.6.6 멱등성·유니크 키 테스트, 11.6.7 늦게 도착한 이벤트와 4일 재적재 창

**책 이론부 포인터** (자세한 설명은 책에서 — 여기에는 요지만)

- 도입(11.1) — 세 장면: 30분째 안 끝나는 쿼리 / "환불 데이터는 아직 분석 DB에 없어요" / 마케팅(Gross)과 재무(Net)의
  매출이 다른 회의. 셋의 공통점은 쿼리 실력이 아니라 데이터 아키텍처·관리 체계의 문제이고, "어떤 질문을 위한
  테이블인가"는 현업이 답해야 한다. 책 11.1 참고.
- 운영 DB에 분석 쿼리를 날리면 안 되는 이유 — 행 저장(트랜잭션) vs 열 저장(집계)의 구조 차이,
  서비스 부하와 조회 지연이라는 두 리스크. 책 11.2.1 참고.
- DW vs Data Lake — 차이의 핵심은 "정리를 넣을 때 하느냐, 꺼낼 때 하느냐". 용어보다 Raw 층과
  Mart/Warehouse 층이 분리돼 있다는 본질이 중요(Lakehouse로 경계는 흐려짐). 방치된 레이크는 Data Swamp. 책 11.2.2 참고.
- 데이터 흐름 — 소스 → 적재 → 저장 → 변환 → 마트·소비, 오케스트레이터가 순서 관리. "DW에 없는
  데이터"는 적재 단계에서 막힌 것이고, 어떤 소스를 먼저 연결할지는 분석가·비즈니스의 몫. 책 11.2.3·그림 11.1 참고.
- 네 층 — src(=raw, 불변·날짜 파티션: 뒤 층의 버그를 수개월 뒤 발견해도 되돌릴 수 있는 유일한 지점이라 손대지
  않는다, 11.3.1) / staging(src 1:1, 이름·타입·중복·잡음만, 보통 뷰, 11.3.2) / dim(설명)·fact(측정, 키만 — 속성을 팩트에
  붙이지 않는 이유는 저장 낭비와 표기 변경 시 일관성, 11.3.3) / mart(질문별 조인·집계, 질문이 고정되는 대가로 빠르고
  싸다, 11.3.4). 팀에 따라 int_ 층 추가. 책 11.3·그림 11.2·표 11.1 참고.
- additive / semi-additive / non-additive — 결제액·건수 / 구독자 수·DAU·잔고(시점 상태) / 전환율·평균 단가.
  책 11.3.3 참고.
- 설계 전제 셋(커버리지↔성능 트레이드오프, 저장은 싸고 사람은 비쌈, 비데이터 직군의 활용 증가)과 좋은 마트의
  조건 넷(주제 분명, 여러 차원으로 쪼개짐, 다른 마트와 중복 없음, 일관·안정). 책 11.4.1 참고.
- 마트 설계 다섯 단계(킴벌 4단계 + 배치) — 업무 프로세스(11.4.2.1) → grain(11.4.2.2) → 디멘션(11.4.2.3) → 팩트(11.4.2.4) →
  배치(11.4.2.5). 예시 "일별 구독자 수"에서 grain을 '일'이 아니라 '구독 이벤트 한 건'으로 잡는 이유(가장 낮은 레벨에서
  어느 방향으로든 올라간다). 11.4.2.4의 측정값 예시는 결제액(현지 통화·USD)·구독 연속 횟수(streak)·건수 — 노트북은
  streak을 뺐다. 11.4.2.5의 배치 체크 질문은 다섯 개(파티션 정의 / 한 배치 = 한 파티션 / 소스 파티션을 필요 이상으로
  읽지 않는가·순환 참조 / 불변 소스 / 테스트). 단계별 산출물·체크 질문·담당은 책 11.4.2·표 11.2 참고 — 아래
  "4. 단계별 진행"의 템플릿이 그 표를 따른다.
- PM·리더의 역할 — 마트가 안 쓰이는 가장 흔한 이유는 기술이 아니라 업무 파트너의 참여 부재. 1·2단계는
  요청자가 함께 채운다. 책 11.4.3 참고.
- 운영 — 한 배치 = 한 파티션(insert-overwrite, 멱등, backfill 단순; 전체 재생성은 데이터가 커지면 비용을 못 견디고,
  UPDATE 배치는 두 번 실행 결과를 확신할 수 없다, 11.5.1) / SCD는 매일 전체 스냅샷(date × user_id, 11.5.2) / 조용히
  틀리는 마트(소스 중복으로 매출 2배, 환율 비어 매출 NULL, 새 이벤트가 필터에 걸려 누락)를 잡는 테스트 4종
  (유니크·not null·허용값·freshness) — 배치 뒤에 자동 실행, 11.5.3 / 늦게 도착하는 데이터는 소스는 도착 시각으로
  파티션, 마트는 발생 시각 기준 + 재적재 창(3·7일), 확정 시점("어제 숫자는 3일 뒤 확정")을 미리 공유, 5.4.
  책 11.5.1~11.5.4·그림 11.3 참고.
- 정리하며 — 마트는 만능이 아니다: 설계에 없던 질문은 팩트/디멘션·raw로 내려간다. 당장 할 일은 가장 느리거나
  가장 자주 다시 짜는 쿼리 하나의 grain을 한 문장으로 써 보는 것 — 써지면 설계의 절반이 끝났고, 안 써지면 어디가
  모호한지 드러난다. 정리 표의 주의 사항: grain 선언과 유니크·not null·freshness 테스트가 신뢰의 최소선.

## 내 데이터에 적용 — 인터랙티브 프로토콜

독자의 요구사항 한 줄이나 지금 쓰고 있는 느린 쿼리를 받아, **마트 설계 다섯 단계 템플릿**을 같이 채운다.
코드에서 뽑을 수 있는 것은 먼저 채우고, 비즈니스 맥락만 독자에게 묻는다. 각 단계 결과를 보여주고 확인한 뒤 다음으로 간다.

### 1. 인테이크 — 독자에게 물을 것

- 지금 이 숫자를 어떻게 보고 있는가? (없음 / 누군가의 쿼리 / 대시보드) 무엇이 불편한가? (느림 / 못 봄 / 팀마다 다름)
- 어느 레벨까지 쪼개 보고 싶은가? (플랫폼·국가·상품·채널·체험 여부 …)
- 핵심 지표의 정의 — 예: "구독자"에 체험을 포함하는가, 환불 건은 빼는가
- 소스는 어디인가, 늦게 도착하는 소스가 있는가 (어트리뷰션·스토어 통지 등 → 재적재 창)
- 쿼리를 가져왔다면: 어떤 테이블을 읽는지, CTE 각각이 정리/조인/집계 중 무엇인지 분류한다

| 역할 (노트북 예시명) | 타입 | 의미 | 필수 |
| --- | --- | --- | --- |
| 이벤트/거래 로그 (`subscription_events`) | 행 단위 | grain 후보 — 한 행이 무엇인가 | ✅ |
| 속성 소스 (`user_snapshots`) | 유저 × 날짜 | 디멘션 후보 (천천히 변함) | ✅ |
| 참조 테이블 (`sku`, `exchange_rates`) | 작은 표 | 디멘션·환산 | 선택 |
| `event_time` / `received_time` | timestamp | 늦은 도착 판단 | 권장 |

### 2. 데이터 점검 — 통과 전 분석 시작 금지

```python
import duckdb
con = duckdb.connect()
con.execute("""
SELECT COUNT(*) AS rows, COUNT(DISTINCT <id>) AS ids, MIN(<ts>) AS t0, MAX(<ts>) AS t1,
       COUNT(*) - COUNT(DISTINCT <id>) AS dup_rows
FROM read_csv_auto('<파일>')""").df()
```

통과 기준: 행 식별자가 있거나 만들 수 있다(없으면 grain을 선언할 수 없다) · 시간 컬럼이 있다 · 중복 비율을 알고 있다
· 속성이 바뀌는 엔티티(유저·상품)가 무엇인지 안다.

### 3. 코드 치환 지도

| 앵커 (실습/식별자) | 무엇을 | 어떻게 |
| --- | --- | --- |
| 11.6.3 `stg_*` 뷰 | 소스 파일 경로·컬럼 이름 | 소스 하나당 뷰 하나. 이름·타입·중복·잡음만 |
| 11.6.4 `fact_subscription_events` | grain 한 문장 → 한 행 | 2단계에서 선언한 grain 그대로. 환산(환율 등)은 여기서. 책 11.4.2.4의 streak 같은 측정값은 팩트에 컬럼을 추가해 확장 |
| 11.6.4 `fact_subscriber_daily` | 상태 스냅샷(semi-additive) | "그 시점에 ~인 엔티티 × 날짜"가 필요할 때만 |
| 11.6.4 `dim_user_daily` | 천천히 바뀌는 속성 | 매일 전체 스냅샷 + `_latest` 뷰 |
| 11.6.4 `dim_sku` | 참조 테이블(상품 마스터) | staging을 그대로 복사 — 독자의 참조 테이블도 같은 방식 |
| 11.6.5 `MART_SQL` | `{partition_date}` 한 파티션 집계 | 1단계에서 정한 레벨(차원)로 GROUP BY |
| 11.6.7 `window_days` | 재적재 창 | 소스의 최대 지연일 + 1 |

⚠ `MART_SQL`의 `{received_filter}` 자리는 11.6.7에서만 채운다 — 실무 배치에서는 비워 둔다.

### 4. 단계별 진행

1. **업무 프로세스** — 현 상황·어려움·보고 있는 지표와 레벨·추가로 볼 지표를 한 장으로. 업무 파트너와 이야기했는지 확인.
2. **Grain 선언** — "One row per …" 한 문장. 가장 낮은 레벨(이벤트)을 권하고, 기존 마트와 겹치는지 묻는다.
3. **디멘션** — 누가·무엇을·어디서·언제·왜·어떻게. 별도 디멘션으로 뺄 키(유저·상품)를 표시.
4. **팩트** — 측정값 목록 + additive / semi-additive / non-additive 구분.
5. **배치** — 파티션 키, 전체/증분/뷰, 한 배치 = 한 파티션, 소스 파티션을 필요 이상으로 읽지 않는지(순환 참조),
   불변 소스, 테스트(유니크·not null·허용값·신선도), 재적재 창. 책 11.4.2.5 체크 질문 다섯 개.
6. 산출물은 아래 템플릿을 채운 마크다운 한 장. 쿼리를 가져온 경우 CTE를 staging / fact / mart로 분류한 표를 덧붙인다.

```markdown
# 마트 설계 — <마트 이름>
## 1. 업무 프로세스 (Select the Business Process)
- 현 상황: / 어려움: / 현재 보는 지표와 레벨: / 추가로 볼 지표:
- [ ] 업무 파트너와 직접 이야기했는가  [ ] 운영 프로세스가 실제로 존재하는가
## 2. Grain (Declare the Grain)
- One row per …
- [ ] 한 문장인가  [ ] 1의 프로세스를 대부분 포함하는가  [ ] 기존 모델과 겹치지 않는가
## 3. 디멘션 (Identify the Dimensions)
- 누가: / 무엇을: / 어디서: / 언제: / 왜·어떻게:
- [ ] 별도 디멘션 테이블로 뺄 키  [ ] 기존 디멘션과 겹치지 않는가
## 4. 팩트 (Identify the Facts)
- 측정값 (additive / semi-additive / non-additive 표시)
- [ ] 1의 지표를 전부 담았는가  [ ] 기존 팩트와 겹치지 않는가
## 5. 배치 (Define Batch Process)
- 파티션 키: / 방식(전체·증분·뷰): / 재적재 창: / 테스트: / 스케줄:
- [ ] 파티션이 정의됐는가  [ ] 한 배치 = 한 파티션  [ ] 소스 파티션을 필요 이상으로 읽지 않는가(순환 참조 없음)  [ ] 불변 소스  [ ] 테스트 정의
```

### 5. 결과 해석

- grain 한 문장이 써지지 않으면 마트가 아니라 **정의**가 없는 것이다 — 1·2단계로 돌아간다.
- 같은 grain의 마트가 이미 있으면 새로 만들지 말고 디멘션·팩트를 **붙이는** 쪽을 먼저 검토한다.
- 재적재 창이 0이 아니면 "어제 숫자는 아직 바뀔 수 있다"를 대시보드·회의에서 같이 안내한다(책 11.5.4: "어제 숫자는 3일 뒤 확정").
- 마트는 설계된 질문만 답한다(책 정리하며) — 설계에 없던 질문은 새 마트를 급조하지 말고 팩트/디멘션·raw로 내려가
  답하고, 반복되면 기존 마트에 차원을 붙이는 쪽을 검토한다.
- 산출물의 최종 확인은 업무 파트너와 한다(책 표 11.2 담당 열: 1·2단계는 PM·업무 파트너 + 분석가, 5단계는 엔지니어 + 분석가).

## 함정

- staging에 비즈니스 로직(예: "체험 유저 제외")이 한 줄 들어가는 순간 정의가 두 곳이 된다 — 팩트/마트로 내린다.
- semi-additive 값(활성 구독자·DAU·잔고)을 날짜를 가로질러 SUM하면 안 된다. 주간은 합이 아니라 마지막 날 값이나 평균.
- DELETE 없이 INSERT만 하는 배치는 두 번 실행되면 중복된다(11.6.6). 유니크 키 테스트가 없으면 조용히 틀린다.
- 배치 성공 ≠ 숫자 정상(책 11.5.3) — 소스 중복으로 매출 2배, 환율 테이블이 비어 그날 매출 전부 NULL, 새 이벤트 유형이
  필터에 걸려 누락. 허용값 테스트는 새 값이 들어오면 **실패하도록** 만들어 선제 감지한다.
- 증분(insert-overwrite) 대신 전체 재생성이나 변경 행 UPDATE 방식을 고르면 데이터가 커질 때 비용, 두 번 실행 시
  결과 불확실이라는 문제가 생긴다(책 11.5.1).
- DuckDB 문법: `DATE + BIGINT`는 안 된다(CSV 정수는 BIGINT로 들어옴 → `CAST(... AS INTEGER)`), 파티션 펼치기는
  `UNNEST(generate_series(start, end, INTERVAL 1 DAY))`.
- 노트북 규모에서는 raw 쿼리도 1초 안에 끝나 "30분"은 재현되지 않는다 — 구조·재현성 차이를 보여주는 실습이다.
- 11.6.7은 구독 이벤트 쪽 숫자(구매·갱신 건수·매출)만 지연이 반영된다 — 활성 구독자 수까지 보려면
  `fact_subscriber_daily`를 다시 만들어야 한다.
- 마트는 설계된 질문만 답한다 — 일·플랫폼·국가로 집계한 마트로는 시간대·앱 버전을 못 본다. 커버리지와 성능은
  트레이드오프이고, 마트에 없는 질문은 팩트/디멘션이나 raw로 내려간다(책 11.3.4·11.4.1).
- 빠른 해결을 위해 비슷한 주제의 마트를 하나 더 만들면 같은 지표가 마트마다 다른 숫자를 내는 날이 반드시 온다 —
  기존 마트 수정을 먼저 검토(책 11.4.1).
- 실습의 `fact_subscriber_daily`는 해지·환불일을 유저당 최초 1회(MIN)로 잡는 단순화 — 재구독 유저가 조용히 사라진다.
  실무에서는 해지를 직전 구독 기간에만 매칭하도록 보완(노트북 11.6.4 주석).
- 늦게 도착하는 데이터에서 소스 파티션을 발생 시각으로 잡으면 소스 불변 규칙이 깨진다 — 소스는 도착 시각,
  마트는 발생 시각 + 재적재 창(책 11.5.4).

## 학습 가이드

### 핵심 개념 — 이 장을 마치면 설명할 수 있어야 하는 것

- 네 층(raw·staging·dim/fact·mart)의 역할과 각 층이 **하지 않는 일**
- grain 한 문장이 왜 설계의 절반인가, 가장 낮은 레벨로 잡는 이유
- additive / semi-additive / non-additive
- 한 배치 = 한 파티션(멱등성)과 backfill, 매일 스냅샷으로 SCD를 푸는 방식
- 늦게 도착하는 데이터와 재적재 창, 테스트 4종(유니크·not null·허용값·신선도)

### 개념 체크

1. 동료가 staging 뷰에 "체험 유저는 구독자에서 제외"하는 WHERE 절을 추가하자고 한다. 어느 층에 들어가야 할 로직이고, staging에 넣으면 어떤 문제가 생기는가?
   - 힌트: 정의가 두 곳 — 누군가는 staging을, 누군가는 마트를 믿는다.
2. "일별 구독자 수"가 목표인데 grain을 '이벤트 한 건'으로 잡았다. '유저 × 날짜'로 잡았을 때와 비교해 무엇을 얻고 무엇을 잃는가?
   - 힌트: 드릴다운과 재집계 vs 테이블 크기.
3. 마트의 `active_subscribers`를 주간으로 보려면 어떻게 해야 하는가?
   - 힌트: semi-additive.
4. 배치가 두 번 실행됐다. `run_partition`은 왜 안전하고, INSERT만 하는 배치는 왜 위험한가?
   - 힌트: 11.6.6의 유니크 키 위반 70건.
5. 어트리뷰션이 설치 후 최대 3일 뒤에 확정된다. 배치와 대시보드에서 각각 무엇을 바꿔야 하는가?
   - 힌트: 재적재 창 + "어제 숫자는 확정치가 아니다".
